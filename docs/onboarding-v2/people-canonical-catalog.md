# Canonical People catalogue and automatic V3 projection

V2 remains the only classification writer and preserves its existing `ClassificationStore` validation, revision, append-only audit, process queue and exclusive source-file lock. `/api/people-catalog` under the V2 namespace authenticates the same signed corporate cookie and exact tid+oid role mapping. GET returns operational fronts, participations and their sanitized audit only; POST requires coordinator, exact Origin, current revision, `confirm:true` and one of the six front/participation CRUD actions. It cannot import research, submit identities, create access roles or return research/evidence bodies.

`V2_CATALOG_PROJECTION_FILE` enables a minimal export under the **same canonical lock**. On startup/snapshot access the writer repairs a stale/missing projection; after every catalogue mutation (including existing endpoints) it atomically publishes and reads back the reduced snapshot. The projection contains only schema/revision, active-state front labels and staffing participation fields plus source/hash/source-date/publication provenance. No person names/emails, notes, audit, research, permissions or raw evidence cross this boundary. A projection hash is integrity metadata, not a signature or proof of business approval.

V3 continues to use its existing `ReadOnlyCatalogAdapter` and existing read-only directory mount; it is not restarted and no V3 code, broker, roles or documentary data changes. The V2 export layer explicitly grants its writer access to the projection directory, masking the unrelated Azure source file read-only. Mount the directory rather than a replaceable file inode. There is one authoritative writable catalogue and one derived, replaceable, read-only staffing projection, not a second personnel store.

Startup and canonical snapshot preflight fail closed on a corrupt or ahead-of-canonical projection. Export does not expire locks or roll back revisions. If publication fails **after** a canonical commit, the dedicated API returns 503 with `committed:true` and the committed revision; the UI must reload/reconcile, never blindly replay creation. A subsequent GET repairs projection from canonical state without adding decisions or changing source revision. No cross-service ACID/power-loss guarantee is claimed: a crash between canonical rename and projection rename is recovered from the canonical snapshot. Only the owning writer may publish; never launch maintenance processes against this path without the same lock.

Apply `deploy/people-catalog.override.yml` after all six incumbent V2 overlays, preserving the exact private env files, roles, existing volume, flags, public-directory scope and Azure project policy. Back up volume/config/projection immediately and compare all canonical/expediente/role/broker bytes after deployment. Initial export publishes existing confirmed catalogue only, never activates people or accepts proposals. Image-only rollback must not restore an old catalogue or projection over newer human decisions.

Tests: `node --test test/v2-catalog-projection.test.js test/v2-people-catalog.test.js`; inherited classification/research/staffing suites; dashboard Chromium uses actual V2 writer → persisted reduced export → unmodified actual V3 read-only adapter and staffing.
